# PPTX export — design

**Date:** 2026-08-25
**Status:** approved, not yet implemented

Export a deck as a PowerPoint `.pptx` file: native, editable slides carrying the
deck's theme, with the theme's celestial backdrop as each slide's background
image.

## Decisions

Four choices settled before design, in the order they constrain everything else:

1. **Native editable slides**, not images of slides. A person who opens the file
   in PowerPoint can click a heading and retype it. The cost, accepted: the 12
   hand-designed layouts are approximated rather than reproduced.
2. **Five PPTX layouts**, not twelve. The 12 on-screen layouts group down to
   `title | body | stat | twoCol | quote`. `visualStyle` is ignored — the two
   treatments are a screen-only distinction.
3. **The backdrop is a background image.** Celestial decoration cannot be
   expressed as native PowerPoint shapes without disproportionate work, so it is
   rasterized to one PNG and set as the slide background, with editable text on
   top.
4. **Two entry points** — the editor's TopBar, and a menu on the dashboard's
   deck card.

The backdrop PNG is produced by a **purpose-built SVG emitter**, not by
screenshotting the live `SlideBackdrop` component. Rasterizing the real
component (via `html-to-image` or similar) means inlining computed styles into
an SVG `foreignObject`; the backdrops are stacks of CSS radial-gradients, which
is the case that path handles worst, and it is weakest in Safari. A
self-contained SVG built from the same `CelestialDecor` data has no
`foreignObject`, cannot taint the canvas, and renders identically everywhere.

The cost of that choice is a second rendering of the backdrop that could drift
from `SlideBackdrop`. Two things bound it: both renderers read the same
`CelestialDecor` object, and the star field's generator is shared outright (see
*Shared star generator* below).

Rejected: pre-rendering five PNGs into `public/`. Almost no code and no runtime
risk, but the images must be regenerated by hand whenever a theme changes, with
nothing to catch it if nobody does — the silent-drift failure this codebase
consistently designs against.

## Module map

```
src/export/
  pptx.ts               orchestrator: Card[] + ThemeTokens -> .pptx Blob -> download
  slideGroup.ts         LayoutType -> 'title'|'body'|'stat'|'twoCol'|'quote'   (pure)
  slideRenderers.ts     the five renderers: (slide, card, theme, style) => void
  textRun.ts            TextStyle + Mark[] -> pptxgenjs text options           (pure)
  backdrop/
    glow.ts             CSS radial-gradient -> SVG <radialGradient>            (pure)
    celestialSvg.ts     CelestialDecor -> a 1920x1080 SVG string               (pure)
    rasterize.ts        SVG string -> PNG data URL                   (the only impure file)
```

Three boundaries this module holds:

- **Nothing in `src/export/` imports React or a component.** It takes `Card[]`
  and `ThemeTokens` and returns a Blob. This is what makes the dashboard entry
  point cheap: no editor, no mounted canvas, no `ThemeProvider`.
- **Nothing outside `src/export/` imports `pptxgenjs`.** The writer stays
  swappable and the dependency stays confined to one file.
- **`pptx.ts` loads `pptxgenjs` through a dynamic `import()`.** It is roughly
  1 MB; someone who never exports should not carry it in the main bundle. The
  trigger's spinner covers the chunk fetch.

Everything except `rasterize.ts` and `pptx.ts` is pure and unit-testable with no
DOM.

**Dependency added:** `pptxgenjs` (4.0.1). It is the only mature browser-side
`.pptx` writer, and it covers native text boxes, shapes, fonts and slide
background images. No rasterization dependency is added — approach B needs none.

## Backdrop pipeline

**One PNG per deck, not per slide.** The backdrop depends only on the theme, and
every PPTX slide is 16:9, so it is rendered once and reused as the background of
all N slides. A 30-card deck carries one image.

**Size is 1920x1080**, roughly 192 DPI against pptxgenjs's default 10in x
5.625in slide.

**Layer order is copied from `SlideBackdrop`** so the two can be compared by
eye: glow, grid, orbits, bodies, stars, constellation.

### Glow

`celestial.glow` is an opaque CSS string authored per theme. All 17 gradient
layers across the five themes share one exact grammar:

```
radial-gradient(W% H% at X% Y%, rgba(r,g,b,a) P%, rgba(r,g,b,0) Q%)
```

`glow.ts` parses that into an SVG `<radialGradient>`, with a `gradientTransform`
carrying the elliptical `W% H%`. A test asserts every `BUILTIN_THEMES` glow
parses — which is also what catches someone later authoring a glow shape the
parser cannot read.

**An unparseable layer is skipped, never thrown.** A slightly plainer background
beats a failed export, and the export must never depend on decoration
succeeding. A theme with no `celestial` at all (which `resolveTheme` should make
impossible) yields a solid `colors.background` fill.

### What the fixed aspect ratio removes

`celestial.ts` and `SlideBackdrop` carry three workarounds that exist *only*
because cards have no fixed aspect ratio. A PPTX slide does, so the SVG emitter
drops all three:

- No `preserveAspectRatio="none"`, so the constellation's vertices become real
  `<circle>` elements in the same SVG rather than the separate
  absolutely-positioned divs `SlideBackdrop` needs today.
- No `aspect-ratio: 1` juggling for orbits and bodies — they are `<circle>` with
  honest radii.
- No `vector-effect="non-scaling-stroke"`.

`body.blurPx` becomes an SVG `<filter><feGaussianBlur>`.

### Shared star generator

`starFieldCss(seed, field)` currently runs its seeded generator and emits a CSS
string in the same loop, so an SVG emitter would have to reimplement the
generator to get the same sky.

Split it: extract `starPositions(seed, field) -> { x, y, radius, alpha }[]` and
have `starFieldCss` map over that. `celestialSvg.ts` consumes the same
`starPositions`.

This closes the drift risk for the largest piece of the backdrop — the exported
sky cannot differ from the on-screen sky, because it is one generator with two
encodings rather than two generators. `starFieldCss`'s own output must not
change. `celestial.test.ts` asserts against its behaviour rather than a golden
string (star count, determinism per seed, circular radii, opacity bounds,
centre keep-out), so it covers the refactor as written and needs no changes.

### Rasterizing

`SVG string -> data URL -> new Image() -> canvas.drawImage -> toDataURL('image/png')`.

The SVG is fully self-contained: no external references, no `foreignObject`, no
webfonts. The canvas is therefore never tainted and `toDataURL` cannot throw on
a security error — which is the concrete reason this approach was chosen over
screenshotting the live component.

## Grouping (`slideGroup.ts`)

`card.layout` is `'auto'` for nearly every card. The export **must** call
`resolveLayout(card.layout, card.blocks, { isFirstCard: i === 0 })` first, or it
classifies the literal string `'auto'` and every slide lands in the wrong group.

| resolved layout | group |
| --- | --- |
| `hero`, `textFocus` | `title` |
| `standard`, `standardSplit`, `timeline`, `iconGrid`, `numberedList`, `gallery` | `body` |
| `statHero`, `statGrid` | `stat` |
| `comparison` | `twoCol` |
| `quote` | `quote` |

Expressed as an exhaustive `Record<Exclude<LayoutType, 'auto'>, PptxGroup>`, so
adding a 13th layout is a type error rather than a silent fallthrough into
`body`.

## The five renderers

Each is `(slide, card, theme, style) => void`, placing text boxes on the
10in x 5.625in slide with a 0.6in margin.

- **title** — heading centred at h1 scale, the card's first `paragraph` beneath
  as a subtitle. A card with no paragraph renders the heading alone, vertically
  centred.
- **body** — heading top-left with a thin accent rule under it; the remaining
  blocks flattened into one bullet text box. The flattening: `paragraph` to an
  unbulleted line, `bulletList` to its items, `timelineStep` to `label — text`,
  `comparisonGroup` to its heading plus indented items, `stat` to
  `value — label`, `image` to its `alt` as a placeholder line — an image with no
  `alt` is skipped, since a bullet reading "image" is worse than no bullet.
- **stat** — the value large and centred in `accent`, label beneath in `muted`.
  `statGrid`'s stats lay out in a row of at most four columns, wrapping to
  further rows beyond that.
- **twoCol** — heading, then the two `comparisonGroup`s as half-width bullet
  boxes under their own headings. A card carrying more than two groups renders
  the first two; the classifier does not produce that case today, but the
  renderer must not throw if it ever does.
- **quote** — quote text centred and large, attribution beneath in `muted`, or
  omitted when the block has none.

## Text and theme mapping (`textRun.ts`)

- **Precedence is the screen's.** `mergeTextStyle(deckStyle, card.textStyle)`,
  then the run's own `inline[ref].style` on top. Reusing `mergeTextStyle` keeps
  the export from becoming a fourth opinion about what a card looks like,
  alongside the canvas, the thumbnails and the presenter view.
- **Font.** A CSS stack (`"'Inter', system-ui, sans-serif"`) must become a
  single PowerPoint face name: take the first family, strip quotes. Same
  treatment for `theme.typography.headingFont` and `bodyFont`. Fonts are **not**
  embedded — a machine without Inter gets PowerPoint's substitute, which is
  normal for `.pptx` and not worth the file size to avoid.
- **Size.** `theme.typography.scale` is `[h1, h2, h3, body]` in rem; PPTX wants
  points. One `PT_PER_REM` constant, chosen so body lands at 18pt, with
  h1/h2/h3 following the theme's own ratios — the same argument `textStyle.ts`
  already makes for scale being a multiplier rather than an absolute size.
  `fontScale` multiplies on top.
- **Inline marks need no new logic.** `textSegments(text, marks)` already
  returns exactly the shape pptxgenjs's rich-text array wants:
  `[{ text, options: { bold, italic } }]`.
- **Colours.** `foreground` for body, `muted` for secondary, `accent` for stat
  values and rules; hex with the `#` stripped. These already clear WCAG AA
  against `theme.colors.background`, and the backdrop PNG is the same artwork
  the app puts behind them, so the existing contrast work carries over
  unchanged.

## Entry points

**Editor TopBar** — an `Export` button beside Present, reading the live store
(`cards`, `theme`, `title`, `textStyle`). It exports what is on screen,
including edits not yet persisted.

**Dashboard `DeckCard`** — needs deck content the dashboard does not hold. It
must **not** call `loadDeck`: `presentationStore` is a single-deck store, and
loading another deck to export it would overwrite the one the user has open.

Extract the query-and-mapping half of `loadDeck` into
`fetchDeck(id): Promise<DeckContent>`, leaving `loadDeck` as
`set(await fetchDeck(id))`. One query path with two consumers, and no second
place for the row-to-`Card` mapping (`resolveTheme`, `parseTextStyle`, the
`visual_style` default) to drift.

`DeckCard` has no menu today, only a bare delete button. This adds a small
overflow menu holding Present / Export as PowerPoint / Delete, with the existing
delete moving into it.

Both entry points call one `useExportPptx()` hook owning `idle | working |
error`, so the spinner, the disabled state and the error message are written
once rather than twice.

Filename is the slugified deck title, falling back to `presentation.pptx` when
the title is empty.

## Error handling

Export is entirely client-side, so there are only two real failure modes:

- The dynamic `import('pptxgenjs')` fails (offline, or the chunk 404s).
- `fetchDeck` fails, on the dashboard path only.

Both surface as an inline message on the trigger, not a modal — the user has
lost nothing and can retry.

Decoration failures never fail the export: an unparseable glow layer is skipped,
and a missing `celestial` falls back to a solid fill. A deck with zero cards
disables the button, matching the editor's existing empty state.

## Testing

Matching this repo's narrow convention of unit tests for pure, high-value logic
only:

- `slideGroup.test.ts` — every layout maps to a group; `auto` resolves through
  `resolveLayout` first; the record is exhaustive.
- `glow.test.ts` — every `BUILTIN_THEMES` glow string parses; a malformed string
  returns `null` rather than throwing.
- `celestialSvg.test.ts` — each theme emits exactly the decor kinds it declares
  and no others, mirroring the restraint rule `theme-tokens.test.ts` already
  holds; output is deterministic for a given theme id.
- `textRun.test.ts` — precedence deck < card < inline; CSS stack to single face
  name; marks to segment options.

No tests for `rasterize.ts` or `pptx.ts`: canvas and a binary writer, which is
where this repo already draws its line (see the coverage note in `CLAUDE.md`).

Verified by hand instead: export a deck under each of the five themes, open each
in PowerPoint, and confirm the text is editable and the backdrop matches the
editor.

## Out of scope

- Embedding fonts in the `.pptx`.
- Speaker notes. `ScriptPanel` still has no source behind it; when it gains one,
  notes become a small addition to each renderer.
- Reproducing `visualStyle`'s two treatments.
- Importing `.pptx`, or any round-trip back into the app.
- Exporting a subset of slides. The unit is the deck.
