### Environment

- `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` in `.env` (see `.env.example`) enable Supabase persistence. If absent, `supabaseConfigured` (`src/lib/supabaseClient.ts`) is `false` and every store method that touches Supabase no-ops gracefully — but this no longer means the app is usable: since accounts are required (see below), an unconfigured Supabase means nobody can ever log in, so `/login` just shows an explanatory message instead of a form. The graceful no-op behavior still matters for the Supabase-backed store methods themselves, just not as a full offline/in-memory mode anymore.
- **Both** provider keys come from `.env` and both are now live — `VITE_GROQ_API_KEY` (`GroqProvider`, primary) and `VITE_GEMINI_API_KEY` (`GeminiProvider`, fallback); see **Provider fallback** below. Either may be omitted, which simply drops that provider from the chain, but at least one is required or `/new` refuses before the first question. Both are read directly in `CreatePage.tsx` (baked into the client bundle at build time — convenient for local/personal dev, but readable by anyone with access to the built app, so don't rely on it for a deployment other people can reach). There is no in-app way to enter a key anymore (the old Settings modal was removed) and no server-side proxy for AI calls by design; the key is sent directly from the browser to the provider's API.
- Accounts are required: every route except `/login` and `/reset-password` is wrapped in `<RequireAuth>` (`src/components/auth/RequireAuth.tsx`), which redirects unauthenticated visitors to `/login`. There is no anonymous/guest mode. Auth state lives in `src/store/authStore.ts` (email/password via Supabase Auth, email confirmation required — toggle at Auth → Providers → Email → "Confirm email" in the Supabase dashboard). `ensureSession()` in `supabaseClient.ts` only waits for the client's session to finish hydrating from storage; it no longer creates a session itself.

## Architecture

This is a Gamma-style AI presentation generator: describe a topic once, get a full deck, then refine and present it. **Generation happens once and is never repeated** — a deck's cards come from a single AI call at creation time, and nothing afterwards rewrites them with the model or triggers a new generation. To get *different* content on the topic, start a new project.

What the user can do by hand has grown well past that, and the two are not in tension: the AI writes, the user edits. Text is editable in place (Level 3), cards can be deleted and reordered from the outline rail, elements can be nudged, and a slide can be **added by hand or changed to another type** — see *Card types* below. Every one of those is the user's own typing or choosing; none of them calls a provider. The rule that still holds absolutely is that no code path asks the model for content a second time.

The direction of authority is the point: the AI decides what a card says and which blocks it holds, and the layout engine decides how that renders. That still holds with element nudging in place, because a nudge is a **delta from** the layout rather than a replacement for it — the classifier runs for every card, every untouched element is placed entirely by its layout component, and switching a card's layout variety re-arranges everything with the nudges still riding on top. There is deliberately no free-form mode and no separate canvas: elements are manipulated on the slide as it already looks.

### Data flow: creation → generation → storage

1. `pages/CreatePage.tsx` — a chat-bubble-style conversational intake (not a form): topic → slide count (a number, or "let AI decide" → `'auto'`) → audience → detail level → tone → optional free-text guidance (what to focus on/avoid), answered one question at a time, each revealing the next. Answers are **editable after the fact** — every answered step carries an Edit affordance that reopens just that step (`editing: StepKey | null`) while leaving the other answers intact; edits lock out while a request is in flight. The six answers live in one `Answers` object persisted through `lib/briefDrafts.ts` (see **Brief drafts** below) on every answer *and* every keystroke, and the draft is deleted once a deck is created. Slide count is capped at `MAX_SLIDES = 30` because `maxOutputTokens` is clamped at 8192 anyway — past roughly that many cards the JSON truncates rather than getting a bigger budget. The `VITE_GROQ_API_KEY` check runs on mount, not at submit, so a missing key is reported before the first question instead of after the sixth.
2. On the last answer, `CreatePage.tsx` calls a `FallbackProvider` (`ai/fallbackProvider.ts`) wrapping an ordered chain — **`ai/groqProvider.ts`'s `GroqProvider`** (model `openai/gpt-oss-120b` via Groq's OpenAI-compatible `chat/completions` endpoint) first, then **`ai/geminiProvider.ts`'s `GeminiProvider`** (model `gemini-flash-latest`). See **Provider fallback** below. Watch out while on Groq: its free tier has previously hit an ~8000 TPM cap on larger/auto-sized decks, which is the original reason this app moved to Gemini in the first place — though a saturated window is now retried rather than surfaced as an error (see **Retry policy** below). `AIProvider.generateDeck` takes an optional `AbortSignal`, and both providers honour it — `GeminiProvider` threads it into both the `fetch` and the backoff `sleep`, so Cancel takes effect mid-retry rather than waiting the timer out; `GroqProvider` threads it into its `fetch`. Don't regress that on the Groq side: the create flow's leave-mid-generation prompt tells the user cancelling stops the request, and an ignored signal makes that a lie — the deck lands minutes later and hijacks navigation. `CreatePage` owns the `AbortController`, aborts on unmount, and treats `signal.aborted` as a return to the brief rather than an error. Both providers retry transient 503/429 responses through the shared policy in `ai/retry.ts` (see **Retry policy** below). Either provider is called with a system prompt (`ai/prompts.ts`) plus the user's brief (`GenerationBrief`: audience/detailLevel/tone/slideCount/guidance) — this part is provider-agnostic. `maxOutputTokens`/`max_tokens` scales with `slideCount` (`slideCount * 260 + 800`, clamped 4096–8192; 8192 when `slideCount === 'auto'`) so larger decks don't get truncated mid-JSON. `guidance`, when non-empty, is injected into the user prompt as a hard constraint that overrides the system prompt's general content rules (e.g. it can suppress invented statistics — see `ai/prompts.ts`'s CONTENT QUALITY RULES, which treat numbers as opt-in rather than a default to avoid padding decks with unnecessary invented figures).
3. The response is parsed and validated against a zod schema (`ai/provider.ts`); a card-level refinement requires every card's first block to be a `heading`. On validation failure, one retry is sent with the exact zod error messages so the model can self-correct.
4. `store/presentationStore.ts` (`createDeckFromGeneration`) atomically creates the Supabase `presentations` row and all `cards` rows, then navigates to `/deck/:id`.
5. Also in `createDeckFromGeneration`: `engine/emphasis.ts`'s `applyEmphasis` converts the model's markdown emphasis into real formatting — `*like this*` and `**like this**` both lose their delimiters and gain a **bold** `Mark` over the characters they wrapped, written into `card.inline` under the same `textRef` the editor would have used. Ingest is the only safe place for it: a mark addresses characters by offset, so stripping delimiters at *render* time would leave the stored string and the drawn string disagreeing about where every character is, and the caret, selections and any existing mark would land in the wrong place. Both forms map to bold rather than markdown's bold/italic split, because a deck full of visible asterisks was the problem. The regex requires each run to start and end with a non-space and contain no asterisk of its own, which is what keeps `2 * 3`, a lone `*`, and `* *` out of it. The same pass also runs at the **read** boundary in `fetchDeck`, which is what converts decks created before it existed: content is never regenerated, so a stored row keeps its asterisks, and the read is the only place they can become bold without a migration or rewriting rows nobody touched — the same boundary `resolveTheme` and the `visual_style` default already use. That makes idempotence a requirement rather than a nicety, and it is why a run that **already carries marks** is skipped entirely, delimiters and all: those offsets describe the stored string, so removing two characters from under hand-applied bold would slide every mark onto the wrong letters.

There is intentionally no "regenerate" path — one topic per project. `CreatePage` also has a "skip and start blank" escape hatch (`createDeck`) for an empty project with no AI call.

### Retry policy (`src/ai/retry.ts`)

Both providers hit the same class of transient failure — the model is momentarily overloaded (503) or the key's rate limit is saturated (429) — and both recover the same way, so the policy lives in one module rather than being copy-pasted and drifting. `callGemini` and `callGroq` each wrap their `fetch` in the same loop: retry `RETRYABLE_STATUS` up to `MAX_RETRIES` (3), otherwise throw.

- `backoffDelayMs(attempt, retryAfter)` is the whole policy and is pure, so it's unit-tested directly. Base is exponential (1s/2s/4s). A server-sent `Retry-After` wins **only when it asks for longer** — it knows when the window actually reopens, and retrying into a still-closed door just burns an attempt. It can never *shorten* the wait below the exponential step.
- `Retry-After` comes in two shapes per RFC 9110 (a delay in seconds, or an HTTP-date) and both appear in the wild, so both are parsed; a date already in the past yields 0 rather than a negative wait.
- **`MAX_DELAY_MS` (20s) clamps it.** Groq measures its free-tier TPM cap over a 60s window and will ask for the remainder of it — a minute of dead air under a spinner reads as a hang. The clamp means we may retry early and eat another 429; accepted, because the request surfaces a real error either way and the user's Cancel can cut the wait short.
- `sleep()` is abortable by design — cancelling during backoff must take effect immediately rather than waiting the timer out. This is the same `AbortSignal` the create flow's Cancel button owns, so breaking it makes the cancel-mid-generation prompt a lie.

### Provider fallback (`src/ai/fallbackProvider.ts`)

`FallbackProvider` implements `AIProvider` itself and wraps an ordered chain, so callers see one provider and nothing else in the app knows a chain exists. `CreatePage` builds `PROVIDER_CHAIN` once at module load: Groq first, Gemini behind it, each included only if its key is present.

- **Only a `capacity` failure (429/503) hands off.** `AIProviderError` carries a `kind` (`capacity` | `auth` | `request` | `response` | `unknown`) and the HTTP status, set at each throw site via `kindForStatus`. Falling over on an `auth` failure would be actively harmful: a mistyped `VITE_GROQ_API_KEY` would silently serve every deck from Gemini and the real problem would never surface. `request`/`response` failures would fail identically on the backup and just spend its quota. This is the load-bearing rule and the tests mutation-check it.
- **Cancellation never hands off.** Without the abort check, hitting Cancel during a Groq request would immediately start a Gemini one, and the deck the user walked away from would still arrive — the exact failure the `AbortSignal` plumbing exists to prevent. Both an aborted signal and a bare `AbortError` are treated as cancellation.
- Each provider has already exhausted its own `ai/retry.ts` retries before it throws, so reaching the next link means the first genuinely could not serve the request — the chain is not a way to skip waiting.
- A provider whose key is missing is left **out of the chain** rather than added and allowed to fail. Dropping `VITE_GROQ_API_KEY` therefore makes this a Gemini-only app with no code change, which is what the old "swap the import by hand" comment used to ask for.
- Cost of the feature, accepted: the Gemini key is now inlined into the built bundle too, since `CreatePage` reads it. That's one more key readable by anyone who can load the built app — see the Environment note above.

### Brief drafts (`src/lib/briefDrafts.ts`)

An unfinished creation brief is a **draft**, listed at `/drafts` (`pages/DraftsPage.tsx`) and reachable from the sidebar's Workspace section with a live count badge.

- **Storage is browser-local `localStorage` (`lekturac:brief-drafts:<uid>`), not Supabase** — no table, no RLS, no store methods. That's deliberate but it *is* the module's whole reason for existing: every read/write goes through this one file so swapping in a Supabase table later means rewriting `briefDrafts.ts` and nothing else. Pages only ever touch the exported functions and `useDrafts()`. The tradeoff to keep in mind: drafts don't follow the user across devices, and clearing site data (or Safari's 7-day ITP eviction) drops them. Note also that every write is wrapped in try/catch, so blocked storage degrades to "drafts silently never save" — while the cancel-generation modal tells the user their brief *is* saved.
- **The key is namespaced by user id, and that's load-bearing.** localStorage knows nothing about who's signed in, and `authStore.signOut()` clears only the Supabase session — so a shared key means signing out and letting someone else sign in on the same browser profile hands them your unfinished briefs, topic text and all. Decks can't leak that way (RLS scopes them to `owner_id`); drafts have no such backstop. `storageKey()` returns `null` while the session is still hydrating and every read/write treats that as "no drafts, skip the write" — falling back to an un-namespaced key would rebuild exactly the shared bucket this closes. In practice `RequireAuth` blocks render until `status !== 'loading'`, so the pages only ever see a resolved session.
- The cache remembers *which key* it was built from, and `useAuthStore.subscribe` invalidates on any change of user id. Without both, the previous account's drafts stay on screen (and in the sidebar badge) after a sign-out.
- **`purgeForeignDrafts()` runs on sign-*in*, never sign-out.** Namespacing hides another account's drafts; it doesn't remove the bytes, which stay readable in DevTools. Clearing on sign-out would close that but destroy the user's own unfinished briefs on every sign-out (there's no server copy), so the purge instead fires when the account actually *changes* and drops every `lekturac:brief-drafts:*` bucket that isn't the incoming user's. Signing out and back in as yourself finds nothing foreign and keeps everything. Residual gap, accepted: between one user signing out and the next signing in, the old bucket is still on disk — closing that needs drafts off the device entirely.
- Ordering inside that subscription is load-bearing: cache is dropped, then `listDrafts()` is called to let `drainLegacyKeys()` adopt any pre-namespace drafts, and only *then* does the purge run. Purging first would delete the un-namespaced legacy list (it shares the prefix) before the migration ever saw it. `purgeForeignDrafts` also collects keys before removing them, since removing mid-loop reindexes `localStorage` and skips entries.
- Two pre-namespace keys are drained into the current user's bucket on first read and deleted: `lekturac:create-draft` (the single-slot `Answers` blob) and the un-namespaced `lekturac:brief-drafts` list that briefly replaced it. Whoever is signed in at the time adopts them — the old keys carry no owner, so there's no better answer, and leaving them would mean every account keeps seeing them.
- `BriefDraft` carries `pendingText` alongside `answers`: text typed into the *open* question but never submitted. Only one step is active at a time, so one slot covers all three text fields, and `CreatePage` restores it into whichever step is first-unanswered. Without this, walking away mid-sentence loses the sentence — which is the case the whole feature exists to prevent.
- Nothing expires on a timer. A draft is visible and deletable now, so having one vanish on its own would be worse than keeping it; `MAX_DRAFTS = 30` caps unbounded growth by dropping the oldest instead.
- `saveDraft` silently drops a draft with no answers and no pending text, so merely opening `/new` and leaving doesn't litter the list.
- `useDrafts()` is a `useSyncExternalStore` subscription. `listDrafts()` caches its parsed, sorted array and only rebuilds on mutation (or a cross-tab `storage` event) — that cache is load-bearing, since an unstable snapshot re-renders forever.
- **Leaving `/new` mid-brief is free and prompts for nothing** — the draft is already saved. The only confirmation left is leaving *mid-generation*, because cancelling wastes real work; even then the brief survives as a draft. Resuming is `/new?draft=<id>`, resolved once into a ref so the identity can't change mid-brief and fork into two rows.
- Drafts are deliberately **not** decks and are not merged into the dashboard's list or its `FilterMenu`: `selectDecks()` takes `DeckSummary[]` and its filters assume a real row (sort by name, `updatedAt`), while the grid's cards offer open/present/delete. A draft has no title until the topic is answered, no cards, and exactly one verb — Resume. `components/home/DraftRow.tsx` is its own row for that reason.

### Content model & layout engine (`src/engine/`)

- `contentBlocks.ts` defines `ContentBlock` as a zod discriminated union (`heading`, `paragraph`, `bulletList`, `stat`, `image`, `quote`, `timelineStep`, `comparisonGroup`) and `Card` (`id`, `orderIndex`, `blocks`, `layout`, `visualStyle`, plus the editor's `textStyle`/`inline`/`adjusts`).
- `card.adjusts` holds per-element nudges — see **Element nudging** below. It is absent for a card nobody has edited, which is the normal state.
- `layoutEngine.ts`'s `chooseLayout(blocks, context)` is a **rule-based classifier** (no LLM call) that inspects what block types a card actually contains and picks one of: `hero`, `statHero`, `statGrid`, `comparison`, `timeline`, `quote`, `iconGrid`, `numberedList`, `textFocus`, `gallery`, `standardSplit`, `standard`. `context.isFirstCard` is how the opening card gets a shot at the cinematic `hero` treatment instead of the generic fallback. `resolveLayout` defers to this whenever `card.layout === 'auto'`, which is what nearly every card carries: the AI never names a layout, and the toolbar's Level 2 picker offers varieties of the card's *own* type (`layoutVarieties`) plus an Automatic option that hands it back here. Two things do name a layout — that picker, and a `title` card added anywhere but the front of the deck, which needs an explicit `hero` because the classifier only awards `hero` to the first card (see *Card types*). `cardKindOf` exists for exactly that case: a named layout outranks the blocks when reporting what type a card is, or the toolbar would call a hero slide a text slide. Layout *selection* is orthogonal to `visualStyle` below — neither depends on the other.
- `card.visualStyle` (`'structured' | 'expressive'`) is chosen by the AI per card at generation time (see `ai/prompts.ts`) and gives every one of the 12 layout components a second visual treatment, so a deck doesn't look templated when a layout repeats. `LayoutRenderer` passes it down as each component's `variant` prop; each component branches its own JSX on it (no shared "variant" component — the two treatments are hand-designed per layout). Legacy rows from before this field existed default to `'structured'` at the `loadDeck` read boundary in `presentationStore.ts`, not in the `Card` type itself.
- `components/layouts/LayoutRenderer.tsx` dispatches a resolved layout to its one dedicated component in `components/layouts/*` (`HeroLayout`, `StatHeroLayout`, `StatGridLayout`, `ComparisonLayout`, `TimelineLayout`, `QuoteLayout`, `IconGridLayout`, `NumberedListLayout`, `TextFocusLayout`, `GalleryLayout`, `StandardLayout`, `StandardSplitLayout`). All heading sizes across these are deliberately uniform (`h2`, via the shared `Heading` component in `BlockRenderer.tsx`) except the opening `HeroLayout` (`h1`) — don't reintroduce per-layout heading-size variance.
- Cards in `CardCanvas`/`PresentPage` have **no fixed aspect ratio or height** — they size purely to their content (this was a deliberate reversal of an earlier fixed-16:9-aspect-ratio design; don't reintroduce `aspect-video` on the card container).

### Element nudging (`engine/blockAdjust.ts`, `engine/frameGeometry.ts`, `components/layouts/Adjustable.tsx`, `components/editor/SelectionLayer.tsx`)

Clicking any element on any slide selects it and gives it a selection box with eight resize handles and a rotate handle. There is **no mode to switch into and no separate canvas** — the manipulation happens on the slide exactly as the layout engine already drew it, which is the whole design constraint.

- **An adjustment is a delta, not a position.** `BlockAdjust` is `{ dx, dy, w?, h?, rotation }`, keyed by block index on `card.adjusts`. Storing absolute coordinates would mean deciding where every *other* element goes too, and the point is that the others keep flowing exactly as they did. A delta also survives the card's text being edited or its layout variety being switched.
- **Units are fractions of the card's content width, never pixels.** A card is responsive — wide on a desktop, 800px in a thumbnail, wider again in the presenter — so a pixel offset captured at one width is wrong at every other. Height is a fraction of *width* too, because the card has no fixed height to measure against, and that also keeps a resized element's aspect stable as the card resizes.
- **Displacement is a `transform`; only size participates in layout.** This is what makes "only the element you touched moves" true: a transform is applied after layout, so moving or rotating an element cannot shift its siblings. `width`/`height` deliberately *do* reflow what follows — the element is still in the slide, not floating on top of it.
- **`Adjustable` is a `display: contents` wrapper**, which is why it can be dropped into twelve hand-designed layouts without touching how any of them look: such a box is not laid out at all, so an untouched element renders byte-identically to before the component existed. A real wrapper `<div>` would become the flex child in `HeroLayout` and stretch where the `h1` used to centre, become the grid cell in `StatGridLayout`, and sit illegally between `<ol>` and `<li>` in `TimelineLayout`. The consequence is there is no box of ours to style, so the adjustment is applied **imperatively to the child node itself** — which is also why a first drag can't make anything jump: same node, same place, transform added.
- **Nested holders are guarded against, and the guard is load-bearing.** `BlockRenderer` wraps every block while `Heading` and `StatBlockView` also wrap themselves — they have to, because most layouts render them directly and never go through `BlockRenderer`. A heading reached *through* `BlockRenderer` therefore nested two holders, and since both are `display: contents`, the outer one's first element child was another boxless div: `getBoundingClientRect` returned zeroes and the selection box collapsed to a dot in the corner. `AdjustedIndexContext` makes the inner one step aside, and `measurableNode` walks past any holder regardless.
- **Wrapping has to happen wherever a block is rendered, not just in the primitives.** `Heading` and `StatBlockView` cover most cards, but `HeroLayout` renders its own `h1`/`p`, `TimelineLayout` its own steps, `QuoteLayout` its quote, `NumberedList`/`IconGrid` their lists, `ComparisonLayout` its groups and `GalleryLayout` its figures — all of which were invisible to selection until wrapped. `Heading`/`StatBlockView` derive their block index from the `textRef` they already receive; the layouts pass the index they iterate with.
- **A resize probes the layout at the new size before computing displacement.** This is the subtle one. Most layouts align their children, so an element's position is a *function of its size*: widen a heading inside `items-center` and the layout re-centres it, moving both edges. `measureAt(node, card, size)` asks "where would the layout put this if it were this big?", and the displacement is measured from that. Without the probe the re-centring is mistaken for a drag and the anchored edge slides by half the size change on every resize — the maths in `frameGeometry.ts` is right and the element still moves.
- **`adjustStyle` emits `maxWidth: none` alongside a width.** Nearly every text element carries a readability cap (`max-w-prose`, `max-w-md`, `max-w-lg`, `max-w-2xl`), which silently overrides a plain width: the selection box grows and the text refuses to, which reads as "the resize handles don't work". Only on the axis actually overridden.
- **`frameGeometry.ts` is pure and unit-tested; none of the maths lives in a component.** `resizeFrame` rotates the drag into the element's own axes, applies it to the axes the handle owns, then pins the *anchor* — the opposite corner, or the midpoint of the opposite edge — back where it was. Expressing the rule as an anchor rather than per-handle x/y arithmetic is what makes rotation work for free and keeps the clamp honest: at the minimum size the handle stops dead instead of dragging the element with it.
- **The natural rect is measured, not computed**, because only the browser knows where an element ended up — the position is whatever a layout component decided after the text wrapped. `measureNatural` clears the imperative styles, reads, and restores them inside one layout pass, so nothing is painted in the cleared state. Clearing the transform matters twice over: `getBoundingClientRect` on a rotated element returns its axis-aligned bounds, not its own rectangle.
- **Every gesture is computed from the frame captured at the press**, never the live one. The live frame changes as each move commits, so accumulating against it doubles every delta. `measureBlock.test.ts` pins the round-trip that this depends on.
- **`SelectionOverlay`'s interior is `pointer-events: none`, its border is not.** Dragging an edge moves the element; the middle stays click-through so a caret can still be placed in the text. That split is what covers both verbs with no modifier key and no mode.
- **A nudge that returns to neutral is deleted, not stored as zeroes** — the presence of an adjustment is what routes a card down the export's per-element path, so an element dragged and dragged back must be indistinguishable from one nobody touched.
- **There is one alignment, and it aligns text inside the element.** A row of six buttons that moved the *box* around the slide was built and then removed as redundant: once an element can be dragged, positioning it from a toolbar is a second way to do the same thing. The three text-align buttons remain, and they now scope to the selected element.
- **An explicitly aligned element is stretched to give its text room** (`stretchesInFlexColumn` in `Adjustable.tsx`). Alignment positions a run *inside* its element's box, so an element whose box hugs its text has nothing to move — the normal case in the layouts that centre with `items-center` (structured `HeroLayout`, `QuoteLayout`, `StatHeroLayout`), where clicking "left" stored the value, lit the button and moved nothing. A toolbar reporting a change that did not happen is worse than one that does nothing. Only an element somebody has explicitly aligned is stretched, so an untouched one still gets exactly the size its layout gave it. The restriction to a **column** flex parent is load-bearing: in a row container `align-self` runs down the *vertical* axis, so the same rule would make the stat in expressive `StatHeroLayout` full-height instead of wider. Grid children already stretch on the inline axis and block elements are already full-width, so neither is touched. Residual, accepted: an element in a *row* flex parent still has no room to align in — giving it some means `flex: 1`, which takes width from its sibling rather than using slack that was already there.
- **The lit align button reflects what is *rendering*, not what is stored** (`useRenderedAlign` → `renderedAlign`). Reading the computed `text-align` off the element is the only honest way: `HeroLayout`, `QuoteLayout` and `StatHeroLayout` centre their text with a CSS class rather than a stored value, so walking the stored chain would light "left" on a hero title that is plainly centred — and an element nobody has aligned has no stored value at all, which used to leave all three buttons dark. `normalizeAlign` maps `start`/`end` to left/right and refuses to guess at `justify`.
- Clicking an alignment now always **sets** it and never clears. The old clear-on-re-click became invisible once the highlight followed the rendered value: clearing an explicit centre usually falls back to centre, so the button stayed lit and the click read as broken.
- **The toolbar has four scopes, narrowest first: run → element → card → deck.** The element scope was the missing one, and its absence was the bug: aligning while an element was selected fell through to the card and re-aligned every line on the slide instead of the one thing the user had picked.
- **Element typography lives in `card.inline` under a bare block index** (`blockStyleKey`), beside the per-run entries keyed by full `textRef`. No new column, and no ambiguity — `parseTextRef` requires at least `index:field`, so nothing that reads runs can mistake one for the other. `store.setInlineStyle` serves both scopes unchanged.
- **`Adjustable` applies that style imperatively too**, because `TextStyleScope` styles a whole card through data attributes and inherited custom properties and cannot say "this heading, not the rest of the slide". Sizes ride as `--slide-size-*` so the theme's h1/h2/h3/body ratios survive being scaled, exactly as `TextStyleScope` does one level up. Note that `inline[ref].style` was stored but **never rendered anywhere** before this — Level 3's font/size/align controls wrote to the database and did nothing.
- **`BlockDataContext` (data) is separate from `BlockAdjustContext` (interaction), and the split is load-bearing.** Every surface that draws a slide provides the data — `SlideBody` takes the card as a prop for exactly this reason. When the nudges were read off the editor-only context instead, a moved element sat where the user put it on the canvas and snapped back to its layout position in the presenter view and every thumbnail.
- **Bold/italic marks are read from `BlockDataContext` too, for the same reason.** `EditableText` used to take them from `TextEditingContext`, which `CardCanvas` provides only to the *selected* card and which the presenter and thumbnails never provide at all — so bold rendered while a card was selected and vanished the moment it wasn't. It is the same `card.inline` either way, so nothing is lost mid-edit. This became load-bearing the moment generation started producing marks (see `applyEmphasis`): before that, the only way to make a mark was to be looking at the card that had it.

### Card types (`engine/cardTemplates.ts`, `components/editor/CardTypeModal.tsx`)

A slide can be added by hand and an existing slide can be changed into another type. Both are the same question — "what kind of slide is this?" — so both run through one modal and one table.

- **`layoutEngine.ts` reads a type off a card; `cardTemplates.ts` writes one.** `cardKind` already classified a card's content family and `layoutVarieties` already knew which layouts that family may wear; what was missing was the other direction — what blocks a card of a chosen type starts with, and what happens to the content on a card whose type is changing. Keeping that in its own pure module (no store, no React) is what makes both directly testable.
- **A new card is placeholder text, not a generation call.** `starterBlocks` returns instructional copy ("What this number measures") that the user edits in place with the Level 3 tools that already exist. Adding a slide therefore never reopens the generate-once rule.
- **`title` is the one type that names its layout.** `chooseLayout` awards `hero` only to the first card, so a title slide added at position 9 would silently render as a plain standard slide. `layoutForKind` returns `'hero'` for it and `'auto'` for everything else, whose starter blocks the classifier reaches on its own. `cardTemplates.test.ts` pins that round trip for every type, because a card that renders, saves and exports perfectly well as the *wrong kind of slide* is a failure nothing else in the app notices.
- **A conversion preserves words, not structure.** `contentLines` flattens everything the user wrote (minus the heading, which always stays the heading) and the target's shape decides where each line lands; short cards are padded with that type's own placeholders, since a one-step timeline is not a timeline as far as the classifier is concerned. Structure genuinely cannot survive going from a stat grid to a quote — losing the *words* is the one unacceptable outcome, because nothing here can be regenerated.
- **Prose converted to stats never invents a number.** Each line becomes a stat's *label* under a placeholder `00`. Fabricating a plausible figure would put a statistic on the slide that nobody wrote — the same failure `ai/prompts.ts` treats numbers as opt-in to avoid.
- **`setCardKind` drops the card's `inline` and `adjusts`, deliberately.** Both are keyed by block index, and a reshape moves text to different indices — a surviving mark would bold the wrong characters and a surviving nudge would displace the wrong element, silently and permanently. The modal says so before the click, and undo restores all three (`history.test.ts` covers it).
- **`gallery` can be converted away from but never to.** An image block needs a `url` and nothing in the app can supply one; offering it would hand the user a card of broken images with no way to fix them.
- **The Level 2 layout button now names the card's type** ("Timeline") and its menu names what Automatic resolved to ("Automatic · Numbered list"). Which layouts the menu can offer depends entirely on which type you are standing on, and an icon alone left the user to infer that from the menu's contents after opening it.
- A new slide lands **after the active card**, not at the end of the deck (`withCardAfter`), and the editor selects and scrolls to it. The empty-deck state gained an Add-a-slide button, which is what finally makes `createDeck`'s "skip and start blank" path lead somewhere.

### Theme system: two CSS token namespaces (the main thing to understand before touching styling)

`src/index.css` defines **two parallel sets** of CSS custom properties, both bridged into Tailwind v4 via `@theme inline` (there is no `tailwind.config.*` — Tailwind v4 is configured entirely in CSS):

- **`app-*`** (`--app-background`, `--app-accent`, `--app-font`, `--radius-app`, `--shadow-app`, …) — defined in `:root`, with a light/dark pair. Every piece of editor/app chrome (TopBar, sidebars, buttons, inputs, modals, Home/Create pages) uses `bg-app-*`/`text-app-*`/`rounded-app-*` classes and never changes regardless of any deck's theme. **Light** values come from a fixed five-color palette (text `#13091b`, background `#faf4fb`, primary `#9f50c3`, secondary `#dace95`, accent `#96cb67`). **Dark is a separate, purpose-built palette** (text `#eee4f6`, background `#0a040b`, primary `#8a3caf`, secondary `#6a5e25`, accent `#639834`) — *not* the light palette darkened. An earlier version tried deriving dark values from the light palette's own colors (e.g. reusing `#13091b` as the page background) and it read as visibly purple even at low lightness, because that palette's colors carry real chroma; this dark palette's background is close to neutral black instead. In both themes, `--app-accent` is the primary and `--app-secondary`/`--app-highlight` hold the other two. Three contrast-safe derived tokens exist for the cases the raw fill colors don't cover: `--app-accent-text`/`--app-highlight-text` are the accent/highlight colors nudged so they clear WCAG AA as *text on the page background* (reach for these on copy and icons, `--app-accent`/`--app-highlight` on solid fills); `--app-highlight-foreground` is a dedicated dark-ink color for text sitting *on top of a solid `--app-highlight` fill* (e.g. an avatar badge) — it can't reuse `--app-foreground` because that flips to light text in dark mode, which fails contrast against the mid-brightness highlight green in both themes.
- **App light/dark mode** — `src/lib/appTheme.ts` (zustand, initialized at module load) writes `data-theme="light"|"dark"` onto `document.documentElement`, persists the choice to `localStorage`, and defaults to `prefers-color-scheme` until the user picks a side explicitly. `[data-theme='dark']` in `index.css` overrides only the `app-*` values — `slide-*` deck themes are authored per deck and deliberately unaffected, so a light deck still previews light inside a dark editor. Tailwind's `dark:` variant is rebound to this attribute via `@custom-variant` at the top of `index.css`, so `dark:` utilities follow the in-app toggle rather than the OS setting. `components/ui/ThemeToggle.tsx` is the switch. Note: two surfaces are deliberately hardcoded always-dark and do **not** follow this toggle — the auth screens' `AuthVisualPanel` (the animated left panel on `/login`, which uses the *light* palette's own hex values directly in its styles) and the dashboard's `AppSidebar` rail (`components/home/AppSidebar.tsx`, white-alpha values over a fixed near-black). Both are fixed structural/brand statements: the dashboard layout is built around a dark rail against light content, and flipping the rail in light mode would collapse that contrast. Use `ThemeToggle`'s `onDark` prop for controls placed on either surface.
- **`slide-*`** (`--slide-background`, `--slide-accent`, `--font-slide-heading`, `--radius-slide`, `--shadow-slide`, …) — the *deck's* visual theme, applied only inside a scoped `ThemeProvider` wrapper (`components/theme/ThemeProvider.tsx`), never on `document.documentElement`. `ThemeProvider` renders a `display: contents` div and calls `applyTheme(theme, thatDivRef)` (`lib/theme-tokens.ts`), which sets the `--slide-*` custom properties (plus Tailwind's own global `--spacing` multiplier) as inline styles on that div. **That call must stay in a `useLayoutEffect`** — every `bg-slide-*`/`text-slide-*` class beneath resolves against those properties, so a passive effect (which runs after the browser paints) gave the slide exactly one painted frame styled by the `:root` fallbacks instead of the deck's theme. It reads as a flash of the wrong palette on every mount, in the canvas, the presenter and all of the outline rail's thumbnails at once. Because CSS custom properties cascade through `display: contents` elements, every `bg-slide-*`/`font-slide-*`/`rounded-slide-*` class *inside* that subtree picks up the scoped values, while everything outside it keeps the `:root` fallback. `layouts/*` components use `slide-*` classes exclusively; `components/ui/*` (shared chrome primitives) use `app-*` exclusively.
- Practical effect: switching a deck's theme (`ThemePanel`, now a **preset-only** picker — no manual color/font/radius/spacing controls) restyles only the cards wrapped in that `ThemeProvider` instance, never the surrounding editor UI. `ThemeProvider` is instantiated separately around `CardCanvas` and around the sidebar's card thumbnails (and again standalone in `PresentPage`), each reading the same `store.theme` — plus once per preview inside `ThemePanel`, which is why it also provides the theme as React context and not just as CSS variables.
- `lib/theme-tokens.ts` also exports `darken()` (hex→HSL→hex) used to derive `--slide-canvas-background` (and the app's own static `--app-canvas`) — the page background sits a few HSL-lightness points below the card background so cards read as floating panels with a shadow, in both light and dark presets.
- `BUILTIN_THEMES` is the only source of themes — there's no user-created/custom-theme storage anymore. The five presets are **celestial**: Moonlight, Cosmic Observatory, Deep Space, Solar Flare, Aurora (the `id`s are still `minimal`/`editorial`/`midnight`/`bold`/`sage`, because deck rows key on them — renaming an id would orphan every deck saved under it).
- Deck rows store the whole theme object as JSON, so `loadDeck` runs it through **`resolveTheme(stored)`** rather than casting it: a deck saved before a redesign carries the older shape (no `celestial`, no `accentSoft`), which would throw the moment the backdrop read it. Matching on `id` is complete because themes are preset-only, and it means existing decks pick up design changes instead of freezing on the palette they were created with.

### Celestial backdrops (`lib/celestial.ts`, `components/theme/SlideBackdrop.tsx`)

Each theme carries a `celestial` field describing its backdrop as **layers of CSS and SVG, never an image**. `applyTheme` writes only the atmospheric layer (`celestial.glow`) as a token, `--slide-backdrop-image`; the structured decoration — stars, orbits, bodies, constellations, chart grid — can't be expressed as a custom property, so `SlideBackdrop` reads the theme object itself from `SlideThemeContext` (`components/theme/slideThemeContext.ts`, kept out of `ThemeProvider.tsx` so that file exports only components and fast refresh keeps working).

- **Each theme uses two or three decorative kinds, never all of them** — that restraint is what keeps five themes from reading as one theme in five palettes, and `theme-tokens.test.ts` holds the line on it. Moonlight: a moon and sparse stars. Cosmic Observatory: a chart grid, plotted constellations, orbital arcs. Deep Space: three overlapping nebula fields and the densest star field. Solar Flare: a corona just off the bottom-right corner with its orbital rings. Aurora: aurora bands over a planet's limb and its atmospheric hairline.
- **Positions are percentages of the card and radii are px.** Cards have no fixed aspect ratio (they size to content), so a percentage-sized gradient would stretch a star into an ellipse on a tall card; `circle <r>px` cannot. Orbits and bodies get `aspect-ratio: 1` off a percentage width for the same reason, and the constellation's `preserveAspectRatio="none"` SVG carries `vector-effect="non-scaling-stroke"` so a tall card doesn't thicken its lines horizontally.
- **A star field is one element, not one element per star** — `starFieldCss` composes N tiny `radial-gradient`s into a single `background-image`. A 30-card deck plus its thumbnails would otherwise carry thousands of divs.
- **The sky is seeded on the theme id**, so it is identical across re-renders and between a card, its thumbnail and the theme preview. `Math.random()` here would visibly reshuffle the background on every scroll or theme switch; `celestial.test.ts` pins the determinism.
- Readability is the constraint the decoration answers to: `avoidCenter` keeps stars out of the band where headings sit, and Deep Space's last gradient *darkens* the middle of the card rather than lighting it. Every palette's body, muted, accent-on-fill and surface pairings were checked to clear WCAG AA — three `accentForeground` values and Aurora's `surface` are set to what contrast required, not to what looked tidiest.

`components/theme/SlideSurface.tsx` is the shared card chrome (themed surface + backdrop + content layer). The three places a slide is drawn — `CardCanvas`, `PresentPage`, and `CardOutlineSidebar`'s thumbnails — all route through it, so a theme can't end up half-applied in one of them. It sets `isolate` (the backdrop can never paint over a neighbouring card) and `overflow-hidden` (decoration is clipped to the theme's corner radius); radius, shadow and padding stay with the caller.

`ThemePanel`'s preview cards are **miniature slides, not swatches** — a real `SlideSurface` rendered at 640×360 and shrunk with `transform: scale()`, each in its own `ThemeProvider`. Rendering them small instead would misrepresent every theme, since star radii, ring strokes and grid spacing are all in px.

### Dashboard layout (`pages/HomePage.tsx`)

A two-column app shell: an always-dark `AppSidebar` rail (logo, search, nav slot, account footer) beside a light main column. Below `lg` the rail becomes an off-canvas drawer driven by `open`/`onClose` from `HomePage` — there is deliberately no second, duplicated mobile header, so the markup has one source of truth.

- The rail's `<nav>` holds one **Workspace** section: `Overview` (routes to `/`) and `Drafts` (routes to `/drafts`, count badge from `useDrafts()` read inside `AppSidebar` itself rather than threaded through every page that renders the rail). `AppSidebar` exports `SidebarSection` and `SidebarLink`, already carrying the rail's styling (active pill, count badges), for further groups.
- Deck **search lives in the rail**, not in the panel toolbar, and binds ⌘F / Ctrl+F (the shortcut is advertised by a `<kbd>` chip in the field, so it has to actually work).
- The main column is a title/subtitle block above one bordered panel. The panel's toolbar strip holds a `ViewTabs` segmented switcher (`grid` | `list`) on the left and `FilterMenu` + the New-presentation CTA on the right.
- `components/home/deckFilters.ts` owns the view/sort/recency types and `selectDecks()`, which does search + filter + sort in a single pass so the grid and list views can't drift apart. Anything zero-result routes to `NoDeckMatches`, whose reset clears the search *and* the filters.
- Cards inside the panel use `border border-app-border` + `shadow-sm` rather than the full `shadow-app`; the deep shadow reads as card-in-card against the panel's own surface.
- **A deck's cover is its own first slide, rendered** (`components/home/DeckThumbnail.tsx`) — the same live-scaled trick as the outline rail: a real `SlideStage`/`SlideSurface`/`LayoutRenderer` at 800px shrunk with `transform: scale()`, in the deck's own theme, never a stored screenshot. So it can't drift from the deck, needs no capture step, and a theme change shows up on the next list read. It is what `listDecks` grew a second query for: `DeckSummary` now carries `theme`, `textStyle` and `cover`, the covers fetched for every deck at once with `.eq('order_index', 0)` rather than a round-trip per tile. `order_index = 0` is dependable because `cardMutations.ts` re-derives `orderIndex` from array position, so the sequence never has a hole at the front; a deck with no cards gets `cover: null` and falls back to the lettered `deckSwatch` gradient. Unlike the rail, the frame is a fixed 16:9 and the slide is fitted to its **width**, so a long first card is cropped at the bottom rather than shrunk — a grid of same-size tiles reads as a grid, and nothing is legible at this size anyway. That is a viewport onto a card, not a card forced into a shape; cards still have no aspect ratio of their own. The row→`Card` mapping moved out of `fetchDeck` into a shared `cardFromRow`, so the two read boundaries can't drift on the emphasis pass or the older-shaped-row defaults.

### Canvas (`components/editor/CardCanvas.tsx`)

`CardCanvas` sorts the cards, wraps each in the slide surface, and hands it to `LayoutRenderer` — for every card, adjusted or not. `cardRefs` exists so `CardOutlineSidebar` can scroll a card into view.

Selection works at two levels, but **one press does both**: pressing an element selects that element *and* the card it belongs to. Requiring the card to be selected first is a step no editor asks for, so every card gets the `BlockAdjustContext` provider and only the selected one is allowed to show a box. `TextEditingContext` is still gated on card selection, so a stray click can't start typing into a card nobody chose. Unselected cards still **render** any nudge they carry, which is `Adjustable`'s job either way.

Because a press selects card and element together, the effect keyed on `selectedCardId` must **not** clear the element selection — it would fire immediately after and wipe what the press just chose. Clearing is the job of whatever actually deselects: pressing the card around its elements, or the canvas.

Element selection (`selectedBlockIndex` in `EditorPage`) is held beside `selectedCardId` rather than inside it, because the two clear on different events: picking another card drops the element, but starting to edit text inside that element must not. `Adjustable` stops its own click, so a click reaching the card means the press landed *around* the elements, and that clears the element selection.

**Undo/redo (`past`/`future` in `presentationStore.ts`) is snapshot-based** over the whole `cards` array rather than a list of inverse operations: delete and reorder then need no bespoke undo each, and redo is the same machinery run backwards. It covers card delete and reorder from the outline sidebar, resets on `loadDeck`, and caps at 50. It depends on `persistCardsSync` diffing the previous card list against the next, so a redo of a delete removes the row again and an undo re-inserts it (the id is preserved, so an upsert restores it — no `deleted_at` column, no trash table). History is in-memory and dies with the tab.

Keyboard, all in one `EditorPage` listener that returns early when the event target is an `input`/`textarea`: ⌘Z undo, ⌘⇧Z (or ⌘Y) redo.

`CardOutlineSidebar`'s thumbnails are **not screenshots** — each is the real `LayoutRenderer` output rendered at a fixed offscreen size (800×450) and shrunk with `transform: scale()`, so they're always pixel-accurate to the live card and update instantly with theme/content changes.

Because a thumbnail scales itself to the *measured* width of the rail, that rail's scroll container carries **`scrollbar-gutter: stable`**, and it is load-bearing. Without it, a platform with classic space-taking scrollbars has a feedback loop with no fixed point: the list overflows → its scrollbar appears → every thumbnail loses that width and shrinks → the list fits → the scrollbar goes → the thumbnails grow → it overflows again, at refresh rate. Whether a given deck lands in that window is coincidence of card count and window height, which is what made it look random. Reserving the gutter always makes the content width constant, so a thumbnail's size no longer depends on whether the list overflows.

### Persistence (Supabase)

`supabase/migrations/0001_init.sql` defines `presentations`, `cards`, and `themes` (the `themes` table is legacy/unused now that custom themes were removed — harmless to leave, not read from). `0002_add_visual_style.sql` adds `cards.visual_style` (`not null default 'structured'`), and `0006_add_block_adjusts.sql` adds `cards.adjusts` (`jsonb not null default '{}'`) — run any your project predates. 0006 in particular is required before **any** card write, not just before nudging one: `cardRow` names `adjusts` on every upsert, so an un-migrated project fails on card delete, reorder and undo/redo too. `0007_touch_presentation_on_card_change.sql` makes a card write bump its parent `presentations.updated_at` — 0001's trigger only refreshed `cards.updated_at`, so the dashboard (which lists from `presentations` and both displays *and orders by* that column) never saw a content edit at all. `0008_add_card_narration.sql` adds `cards.narration` (`jsonb not null default '{}'`) — and, exactly like 0006, it is required before **any** card write rather than only before narrating one, because `cardRow` names `narration` on every upsert. An un-migrated project fails on card delete, reorder and undo/redo too. `parseNarration` maps the `{}` default back to `undefined` for the same reason `parseAdjusts` does: a row that has the column is not a row that has a script, and treating it as one would show every pre-existing deck as fully narrated. Note that `default '{}'` means every pre-existing row reads back as an empty record, so `parseAdjusts` maps that to `undefined`: "has an `adjusts` field" is not the same question as "has been adjusted", and treating it as adjusted would route every untouched card down the export's approximate path. RLS on every table is scoped to `owner_id = auth.uid()`, with `cards` checked via a join back to its parent `presentations` row. `store/presentationStore.ts` debounces title and theme (`scheduleSave`, 500ms) but persists structural changes (card delete, reorder, undo/redo) immediately. All card writes go through one `persistCardsSync(presentationId, previous, next)`, which deletes the rows that dropped out of `next` and upserts the rest — a plain upsert cannot express a deletion, which undo/redo crossing a delete in either direction requires.

**A debounced write must never be outrun by a read.** An edit is in memory immediately but in the database 500ms later, and both `EditorPage` and `PresentPage` call `loadDeck` on mount — so pressing Present just after aligning or dragging an element used to re-read the *pre-edit* row and overwrite what the user had just changed. The presenter showed the old value, and worse, the next edit was then computed from the stale card and could drop the first one for real. Three rules close it, and they are load-bearing together:

- **`loadDeck` returns early when it already holds that deck id.** This store holds exactly one deck, so if its id is loaded, the in-memory copy is the newest that exists — the database is the side catching up. Going to the presenter and back now keeps the undo stack too.
- **`flushScheduledSaves()` runs pending writes rather than dropping them**, and `loadDeck` awaits it before reading a *different* deck (whose timers belong to the deck being left). It is the counterpart to `cancelScheduledSaves`, which exists for the opposite reason — undo must stop an *older* value landing last. `EditorPage` also fires it on `beforeunload`, which is best-effort only: the browser will not wait for it.
- **A released gesture is written immediately** — `setBlockAdjust(..., commit)`. The debounce exists only to absorb the adjustment-per-pointer-event a drag produces; once the pointer is up the value is final, and holding it 500ms only widens the window a reload can lose it in. `SelectionOverlay` reports the release through `startPointerDrag`'s `onEnd`, and `SelectionLayer` re-sends the last value with `commit`. The pending debounced copy is cleared first so it cannot land *after* the committed one. It costs one redundant write and adds no undo step, since `pushHistory` coalesces on the same key well inside its window.

`store/saveTiming.test.ts` pins all three against a mocked-but-*configured* Supabase, since what is being checked is the order and timing of calls rather than their absence.

### Narration page (`pages/NarratePage.tsx`, `engine/narration.ts`, `ai/narrationPrompt.ts`)

`/deck/:id/narrate` pairs a read-only slide viewer on the left with a narration script panel on the right: an expanded spoken script per slide, for a cloned voice to read in later development. It is what the previously-disabled "Narrate PPT" button in `TopBar` now opens. Design doc: `docs/superpowers/specs/2026-09-02-narration-page-design.md`.

- **This is a second AI call, and the generate-once rule is unchanged.** The rule is that no code path regenerates a card's **`blocks`** — narration is a separate field that the layout engine never reads, no slide ever renders, and the PPTX export never writes. The deck the user sees still comes from the single call at creation. Do not treat `generateNarration` as precedent for a "regenerate this slide" button.
- **Read-only is achieved by omission, not by a `readOnly` prop.** `SlideViewer` renders the same `SlideSurface`/`SlideBody`/`LayoutRenderer` chain the presenter does and simply does not provide `TextEditingContext` (typing) or the interaction half of `BlockAdjustContext` (selection boxes). Threading a flag through twelve hand-designed layouts would have created a second render path to drift. `SlideBody` is still required — its `BlockDataContext` is what makes stored nudges and bold marks render, and without it the viewer would show a different slide than the one the user arranged.
- **A card stores two scripts, not a script and an `edited` flag.** `narration` is `{ text, generated }`: what a voice will read, and the AI's version of it. `narrationStatus`, `isRegenerable` and `isResettable` are all *derived* from those two, so none of them can fall out of sync — and keeping `generated` is what makes "Reset to generated" literal rather than "clear and hope the next generation refills it".
- **A blank script reads as `empty` even when a generated copy survives**, because the status chip predicts what Generate-all will do and a blanked script *is* rewritten. Reset stays offered on it, so blanking never loses the AI's copy.
- **`mergeNarration` applies a script only to a regenerable slide, whatever the model returned.** The prompt asks it to leave edited slides alone, but a prompt is a request and this is the invariant the feature is sold on; the guard lives in a pure function precisely so a test can fail when someone removes it. Slides the user has edited are still *sent* to the model, marked fixed, because a call that saw only the gaps would write transitions into nothing.
- **The whole deck is one call**, not one per slide: narration that flows slide-to-slide ("that brings us to…") cannot come from N requests that each start cold. `generateNarration` sits on the `AIProvider` interface beside `generateDeck`, so `FallbackProvider` covers it with the existing capacity-only failover, `ai/retry.ts` backoff and abort handling, and a missing key still drops that provider from the chain.
- **The narration token budget is bounded on both sides, and both bounds are measured rather than guessed** (`narrationMaxTokens`). Groq's model here is `openai/gpt-oss-120b`, a *reasoning* model: it spends tokens thinking before it emits anything, and those count against `max_tokens`. An 8-slide deck measured 4532 completion tokens of which 3400 were reasoning — so a budget below roughly 3400 returns an **empty** completion and a 400 `json_validate_failed`, not a shorter script. That is why the floor is 5200 and not the 2048 this shipped with first. The ceiling is 7000 rather than the deck path's 8192 because Groq's free tier advertises `x-ratelimit-limit-tokens: 8000` per minute and counts *requested* output against that window: a request for 8192 is refused outright before the model runs. Residual, accepted: a very large deck can still exhaust 7000, and because that surfaces as a 400 (`request` kind) rather than a 429, it will **not** fall over to Gemini.
- Timing follows the store's existing rules rather than extending them: typing debounces at 500ms and coalesces undo on `narration:<cardId>`, while Reset and a whole generation are written immediately (neither has anything left to coalesce). `NarratePage` calls `flushScheduledSaves()` on unmount so returning to the editor cannot outrun the last sentence typed.
- **The panel surfaces a failed *save*, not just a failed generation.** A narration script is typed by hand and cannot be regenerated, so a silent write failure is the worst outcome available on this page — the user sees their words, reloads, and finds nothing. `NarratePage` therefore folds `store.status === 'error'` into the same `error` prop `ScriptPanel` already renders for generation failures, generation error first. This is how a missing migration 0008 announces itself instead of looking like a page that quietly forgets.
- **Accepted limitation:** the creation brief (audience, tone, detail level) is deleted with the draft once a deck is created and is not stored on the deck, so narration infers tone from the deck's own text.

### PPTX export (`src/export/`)

`exportDeckToPptx(deck)` turns a deck into a `.pptx` of **native, editable**
PowerPoint slides — real text boxes, not pictures of slides. Design doc:
`docs/superpowers/specs/2026-08-25-pptx-export-design.md`.

- **The twelve layouts group onto five arrangements** (`slideGroup.ts`:
  title/body/stat/twoCol/quote). `resolveLayout` runs first — `card.layout` is
  `'auto'` for nearly every card, so grouping on the stored value would classify
  the string `'auto'` and put the whole deck in one bucket. The record is
  exhaustive, so a thirteenth layout is a type error rather than a silent
  fallthrough. `visualStyle` is not represented.
- **A sixth group, `adjusted`, short-circuits all of that.** A card where somebody has moved or resized an element cannot go through the five: `body` in particular merges every block after the heading into one text box, which leaves a per-element offset nowhere to go. The check runs before the classifier does anything. A card nobody has touched takes exactly the path it always did.
- **`export/blockBoxes.ts` is the baseline that path needs, and its limitation is deliberate and documented.** `src/export/` has no DOM and may not import React, so it cannot measure where a layout put an element — and a nudge is a delta from a position it therefore does not know. So it recomputes a plain stacked arrangement in the same normalized space the nudges are stored in, and applies them on top. What survives exactly is the thing the user did: the direction, distance and size of every nudge relative to the card. What does not is the hero or timeline treatment the card has on screen. The card's content-driven aspect ratio is *fitted* into the 16:9 slide and centred rather than stretched, since stretching would distort every nudge this path exists to preserve.
- **Adjusted text is sized by `fittedPointSize`, not `pointSize`.** `PT_PER_REM` lands a body line at a comfortable 18pt whatever box it sits in, which is right for the five arranged layouts (they size their boxes to the text) and wrong here: the user sized these boxes by eye, so text arriving larger than they drew it overflows boxes that fitted on screen. Every adjusted box also carries `fit: 'shrink'`, since overflowing a user-sized box is the expected failure.
- **`starPositions` in `lib/celestial.ts` is shared by both renderers**, so the
  exported sky cannot differ from the on-screen one. The order of its `rand()`
  draws is load-bearing: a star rejected by `avoidCenter` consumes exactly its x
  and y draws, and moving the radius/alpha draws above that `continue` would
  reshuffle all five themes.
- **`pptxgenjs` is dynamically imported and confined to `pptx.ts`.** It is ~1MB;
  nobody who never exports should carry it in the main bundle. The renderers
  depend on a local structural `PptxSlide` interface rather than the library's
  types.
- **Nothing in `src/export/` imports React or a component** (the `useExportPptx`
  hook aside), which is what lets the dashboard export a deck it never opened.
  That path goes through `fetchDeck` and **not** `loadDeck`: this store holds
  exactly one deck, and loading another to export it would overwrite the one the
  user has open.
- Composite body lines (a stat's `value — label`, a timeline step's
  `label — text`) drop their inline bold/italic marks, because they join two
  separately-addressed runs and no single `textRef` applies.

### Auth

`src/store/authStore.ts` is a zustand store, initialized once at module load (subscribing to `supabase.auth.onAuthStateChange`), exposing `user`/`status` plus `signUp`/`signIn`/`signOut`/`resetPasswordForEmail`/`updatePassword`. `resolveAuthState()` treats a session where `session.user.is_anonymous` is `true` the same as no session at all — this matters because browsers that used the app before this feature shipped may still be holding a leftover anonymous Supabase session in `localStorage`, and without this check that stale session would silently satisfy `RequireAuth` and skip the login screen entirely. `LoginPage.tsx` (route `/login`) handles login, signup, and forgot-password as one page via local mode state, rather than three separate routes. `ResetPasswordPage.tsx` (route `/reset-password`) is the landing page for the password-reset email link — Supabase's client auto-detects the recovery session from the URL. Decks created under the old anonymous-auth model (before this feature) are orphaned rows in Supabase, invisible to any real account under RLS — harmless to leave, or delete manually from the Supabase dashboard.
