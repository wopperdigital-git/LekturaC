# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm run dev       # Vite dev server (localhost:5173)
npm run build     # tsc -b && vite build — type-checks before bundling
npm run lint      # oxlint (type-aware rules enabled via oxlint-tsgolint, see .oxlintrc.json)
npm run test      # vitest run
npm run preview   # preview a production build
```

Test coverage is intentionally narrow: Vitest unit tests exist only for pure, high-value logic — `engine/layoutEngine.test.ts` (the layout classifier), `lib/theme-tokens.test.ts` (`darken`/`applyTheme`), `lib/briefDrafts.test.ts` (per-user draft namespacing, the sign-in purge, and the legacy-key migration — storage rules with privacy consequences, exercised against a stubbed auth store and an in-memory `localStorage`), and `ai/retry.test.ts` (the shared backoff policy: exponential steps, `Retry-After` parsing in both its seconds and HTTP-date forms, the clamp, and the abortable `sleep`). No component/integration tests. `.github/workflows/ci.yml` runs typecheck, lint, test, and build on push/PR.

### Environment

- `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` in `.env` (see `.env.example`) enable Supabase persistence. If absent, `supabaseConfigured` (`src/lib/supabaseClient.ts`) is `false` and every store method that touches Supabase no-ops gracefully — but this no longer means the app is usable: since accounts are required (see below), an unconfigured Supabase means nobody can ever log in, so `/login` just shows an explanatory message instead of a form. The graceful no-op behavior still matters for the Supabase-backed store methods themselves, just not as a full offline/in-memory mode anymore.
- The active AI provider's key comes from `.env` — `VITE_GROQ_API_KEY` (`GroqProvider`), `VITE_GEMINI_API_KEY` sits unused alongside it for `GeminiProvider` (see Data flow below for why). Whichever is active is read directly in `CreatePage.tsx` (baked into the client bundle at build time — convenient for local/personal dev, but readable by anyone with access to the built app, so don't rely on it for a deployment other people can reach). There is no in-app way to enter a key anymore (the old Settings modal was removed) and no server-side proxy for AI calls by design; the key is sent directly from the browser to the provider's API.
- Accounts are required: every route except `/login` and `/reset-password` is wrapped in `<RequireAuth>` (`src/components/auth/RequireAuth.tsx`), which redirects unauthenticated visitors to `/login`. There is no anonymous/guest mode. Auth state lives in `src/store/authStore.ts` (email/password via Supabase Auth, email confirmation required — toggle at Auth → Providers → Email → "Confirm email" in the Supabase dashboard). `ensureSession()` in `supabaseClient.ts` only waits for the client's session to finish hydrating from storage; it no longer creates a session itself.

## Architecture

This is a Gamma-style AI presentation generator: describe a topic once, get a full deck, view/reorder/present it. **There is no manual content editing** — a project's cards are generated once at creation time and are read-only afterward in the editor (only reordering and deleting cards is possible). To change content, start a new project.

### Data flow: creation → generation → storage

1. `pages/CreatePage.tsx` — a chat-bubble-style conversational intake (not a form): topic → slide count (a number, or "let AI decide" → `'auto'`) → audience → detail level → tone → optional free-text guidance (what to focus on/avoid), answered one question at a time, each revealing the next. Answers are **editable after the fact** — every answered step carries an Edit affordance that reopens just that step (`editing: StepKey | null`) while leaving the other answers intact; edits lock out while a request is in flight. The six answers live in one `Answers` object persisted through `lib/briefDrafts.ts` (see **Brief drafts** below) on every answer *and* every keystroke, and the draft is deleted once a deck is created. Slide count is capped at `MAX_SLIDES = 30` because `maxOutputTokens` is clamped at 8192 anyway — past roughly that many cards the JSON truncates rather than getting a bigger budget. The `VITE_GROQ_API_KEY` check runs on mount, not at submit, so a missing key is reported before the first question instead of after the sixth.
2. On the last answer, `CreatePage.tsx` calls whichever `AIProvider` (`ai/provider.ts`) is currently wired up — **`ai/groqProvider.ts`'s `GroqProvider`** (model `openai/gpt-oss-120b` via Groq's OpenAI-compatible `chat/completions` endpoint), swapped back in temporarily. `ai/geminiProvider.ts`'s `GeminiProvider` (model `gemini-flash-latest`) is left in place, unused — `CreatePage.tsx` has a comment at its provider import marking exactly what to swap back. Watch out while on Groq: its free tier has previously hit an ~8000 TPM cap on larger/auto-sized decks, which is the original reason this app moved to Gemini in the first place — though a saturated window is now retried rather than surfaced as an error (see **Retry policy** below). `AIProvider.generateDeck` takes an optional `AbortSignal`, and both providers honour it — `GeminiProvider` threads it into both the `fetch` and the backoff `sleep`, so Cancel takes effect mid-retry rather than waiting the timer out; `GroqProvider` threads it into its `fetch`. Don't regress that on the Groq side: the create flow's leave-mid-generation prompt tells the user cancelling stops the request, and an ignored signal makes that a lie — the deck lands minutes later and hijacks navigation. `CreatePage` owns the `AbortController`, aborts on unmount, and treats `signal.aborted` as a return to the brief rather than an error. Both providers retry transient 503/429 responses through the shared policy in `ai/retry.ts` (see **Retry policy** below). Either provider is called with a system prompt (`ai/prompts.ts`) plus the user's brief (`GenerationBrief`: audience/detailLevel/tone/slideCount/guidance) — this part is provider-agnostic. `maxOutputTokens`/`max_tokens` scales with `slideCount` (`slideCount * 260 + 800`, clamped 4096–8192; 8192 when `slideCount === 'auto'`) so larger decks don't get truncated mid-JSON. `guidance`, when non-empty, is injected into the user prompt as a hard constraint that overrides the system prompt's general content rules (e.g. it can suppress invented statistics — see `ai/prompts.ts`'s CONTENT QUALITY RULES, which treat numbers as opt-in rather than a default to avoid padding decks with unnecessary invented figures).
3. The response is parsed and validated against a zod schema (`ai/provider.ts`); a card-level refinement requires every card's first block to be a `heading`. On validation failure, one retry is sent with the exact zod error messages so the model can self-correct.
4. `store/presentationStore.ts` (`createDeckFromGeneration`) atomically creates the Supabase `presentations` row and all `cards` rows, then navigates to `/deck/:id`.

There is intentionally no "regenerate" path — one topic per project. `CreatePage` also has a "skip and start blank" escape hatch (`createDeck`) for an empty project with no AI call.

### Retry policy (`src/ai/retry.ts`)

Both providers hit the same class of transient failure — the model is momentarily overloaded (503) or the key's rate limit is saturated (429) — and both recover the same way, so the policy lives in one module rather than being copy-pasted and drifting. `callGemini` and `callGroq` each wrap their `fetch` in the same loop: retry `RETRYABLE_STATUS` up to `MAX_RETRIES` (3), otherwise throw.

- `backoffDelayMs(attempt, retryAfter)` is the whole policy and is pure, so it's unit-tested directly. Base is exponential (1s/2s/4s). A server-sent `Retry-After` wins **only when it asks for longer** — it knows when the window actually reopens, and retrying into a still-closed door just burns an attempt. It can never *shorten* the wait below the exponential step.
- `Retry-After` comes in two shapes per RFC 9110 (a delay in seconds, or an HTTP-date) and both appear in the wild, so both are parsed; a date already in the past yields 0 rather than a negative wait.
- **`MAX_DELAY_MS` (20s) clamps it.** Groq measures its free-tier TPM cap over a 60s window and will ask for the remainder of it — a minute of dead air under a spinner reads as a hang. The clamp means we may retry early and eat another 429; accepted, because the request surfaces a real error either way and the user's Cancel can cut the wait short.
- `sleep()` is abortable by design — cancelling during backoff must take effect immediately rather than waiting the timer out. This is the same `AbortSignal` the create flow's Cancel button owns, so breaking it makes the cancel-mid-generation prompt a lie.

### Brief drafts (`src/lib/briefDrafts.ts`)

An unfinished creation brief is a **draft**, listed at `/drafts` (`pages/DraftsPage.tsx`) and reachable from the sidebar's Workspace section with a live count badge.

- **Storage is browser-local `localStorage` (`lekturac:brief-drafts:<uid>`), not Supabase** — no table, no RLS, no store methods. That's deliberate but it *is* the module's whole reason for existing: every read/write goes through this one file so swapping in a Supabase table later means rewriting `briefDrafts.ts` and nothing else. Pages only ever touch the exported functions and `useDrafts()`. The tradeoff to keep in mind: drafts don't follow the user across devices, and clearing site data (or Safari's 7-day ITP eviction) drops them. Note also that every write is wrapped in try/catch, so blocked storage degrades to "drafts silently never save" — while the cancel-generation modal tells the user their brief *is* saved.
- **The key is namespaced by user id, and that's load-bearing.** localStorage knows nothing about who's signed in, and `authStore.signOut()` clears only the Supabase session — so a shared key means signing out and letting someone else sign in on the same browser profile hands them your unfinished briefs, topic text and all. Decks can't leak that way (RLS scopes them to `owner_id`); drafts have no such backstop. `storageKey()` returns `null` while the session is still hydrating and every read/write treats that as "no drafts, skip the write" — falling back to an un-namespaced key would rebuild exactly the shared bucket this closes. In practice `RequireAuth` blocks render until `status !== 'loading'`, so the pages only ever see a resolved session.
- The cache remembers *which key* it was built from, and `useAuthStore.subscribe` invalidates on any change of user id. Without both, the previous account's drafts stay on screen (and in the sidebar badge) after a sign-out.
- **`purgeForeignDrafts()` runs on sign-*in*, never sign-out.** Namespacing hides another account's drafts; it doesn't remove the bytes, which stay readable in DevTools. Clearing on sign-out would close that but destroy the user's own unfinished briefs on every sign-out (there's no server copy), so the purge instead fires when the account actually *changes* and drops every `lekturac:brief-drafts:*` bucket that isn't the incoming user's. Signing out and back in as yourself finds nothing foreign and keeps everything. Residual gap, accepted: between one user signing out and the next signing in, the old bucket is still on disk — closing that needs drafts off the device entirely.
- Ordering inside that subscription is load-bearing: cache is dropped, then `listDrafts()` is called to let `drainLegacyKeys()` adopt any pre-namespace drafts, and only *then* does the purge run. Purging first would delete the un-namespaced legacy list (it shares the prefix) before the migration ever saw it. `purgeForeignDrafts` also collects keys before removing them, since removing mid-loop reindexes `localStorage` and skips entries.
- Two pre-namespace keys are drained into the current user's bucket on first read and deleted: `lekturac:create-draft` (the single-slot `Answers` blob) and the un-namespaced `lekturac:brief-drafts` list that briefly replaced it. Whoever is signed in at the time adopts them — the old keys carry no owner, so there's no better answer, and leaving them would mean every account keeps seeing them.
- `BriefDraft` carries `pendingText` alongside `answers`: text typed into the *open* question but never submitted. Only one step is active at a time, so one slot covers all three text fields, and `CreatePage` restores it into whichever step is first-unanswered. Without this, walking away mid-sentence loses the sentence — which is the case the whole feature exists to prevent.
- Nothing expires on a timer. A draft is visible and deletable now, so having one vanish on its own would be worse than keeping it; `MAX_DRAFTS = 30` caps unbounded growth by dropping the oldest instead.
- `saveDraft` silently drops a draft with no answers and no pending text, so merely opening `/new` and leaving doesn't litter the list.
- `useDrafts()` is a `useSyncExternalStore` subscription. `listDrafts()` caches its parsed, sorted array and only rebuilds on mutation (or a cross-tab `storage` event) — that cache is load-bearing, since an unstable snapshot re-renders forever.
- **Leaving `/new` mid-brief is free and prompts for nothing** — the draft is already saved. The only confirmation left is leaving *mid-generation*, because cancelling wastes real work; even then the brief survives as a draft. Resuming is `/new?draft=<id>`, resolved once into a ref so the identity can't change mid-brief and fork into two rows.
- Drafts are deliberately **not** decks and are not merged into the dashboard's list or its `FilterMenu`: `selectDecks()` takes `DeckSummary[]` and its filters assume a real row (sort by name, `updatedAt`), while the grid's cards offer open/present/delete. A draft has no title until the topic is answered, no cards, and exactly one verb — Resume. `components/home/DraftRow.tsx` is its own row for that reason.

### Content model & layout engine (`src/engine/`)

- `contentBlocks.ts` defines `ContentBlock` as a zod discriminated union (`heading`, `paragraph`, `bulletList`, `stat`, `image`, `quote`, `timelineStep`, `comparisonGroup`) and `Card` (`id`, `orderIndex`, `blocks`, `layout`, `visualStyle`).
- `layoutEngine.ts`'s `chooseLayout(blocks, context)` is a **rule-based classifier** (no LLM call) that inspects what block types a card actually contains and picks one of: `hero`, `statHero`, `statGrid`, `comparison`, `timeline`, `quote`, `iconGrid`, `numberedList`, `textFocus`, `gallery`, `standardSplit`, `standard`. `context.isFirstCard` is how the opening card gets a shot at the cinematic `hero` treatment instead of the generic fallback. `resolveLayout` defers to this whenever `card.layout === 'auto'` (the only value anything ever sets it to now — the manual per-card layout override UI was removed). Layout *selection* is orthogonal to `visualStyle` below — neither depends on the other.
- `card.visualStyle` (`'structured' | 'expressive'`) is chosen by the AI per card at generation time (see `ai/prompts.ts`) and gives every one of the 12 layout components a second visual treatment, so a deck doesn't look templated when a layout repeats. `LayoutRenderer` passes it down as each component's `variant` prop; each component branches its own JSX on it (no shared "variant" component — the two treatments are hand-designed per layout). Legacy rows from before this field existed default to `'structured'` at the `loadDeck` read boundary in `presentationStore.ts`, not in the `Card` type itself.
- `components/layouts/LayoutRenderer.tsx` dispatches a resolved layout to its one dedicated component in `components/layouts/*` (`HeroLayout`, `StatHeroLayout`, `StatGridLayout`, `ComparisonLayout`, `TimelineLayout`, `QuoteLayout`, `IconGridLayout`, `NumberedListLayout`, `TextFocusLayout`, `GalleryLayout`, `StandardLayout`, `StandardSplitLayout`). All heading sizes across these are deliberately uniform (`h2`, via the shared `Heading` component in `BlockRenderer.tsx`) except the opening `HeroLayout` (`h1`) — don't reintroduce per-layout heading-size variance.
- Cards in `CardCanvas`/`PresentPage` have **no fixed aspect ratio or height** — they size purely to their content (this was a deliberate reversal of an earlier fixed-16:9-aspect-ratio design; don't reintroduce `aspect-video` on the card container).

### Theme system: two CSS token namespaces (the main thing to understand before touching styling)

`src/index.css` defines **two parallel sets** of CSS custom properties, both bridged into Tailwind v4 via `@theme inline` (there is no `tailwind.config.*` — Tailwind v4 is configured entirely in CSS):

- **`app-*`** (`--app-background`, `--app-accent`, `--app-font`, `--radius-app`, `--shadow-app`, …) — defined in `:root`, with a light/dark pair. Every piece of editor/app chrome (TopBar, sidebars, buttons, inputs, modals, Home/Create pages) uses `bg-app-*`/`text-app-*`/`rounded-app-*` classes and never changes regardless of any deck's theme. **Light** values come from a fixed five-color palette (text `#13091b`, background `#faf4fb`, primary `#9f50c3`, secondary `#dace95`, accent `#96cb67`). **Dark is a separate, purpose-built palette** (text `#eee4f6`, background `#0a040b`, primary `#8a3caf`, secondary `#6a5e25`, accent `#639834`) — *not* the light palette darkened. An earlier version tried deriving dark values from the light palette's own colors (e.g. reusing `#13091b` as the page background) and it read as visibly purple even at low lightness, because that palette's colors carry real chroma; this dark palette's background is close to neutral black instead. In both themes, `--app-accent` is the primary and `--app-secondary`/`--app-highlight` hold the other two. Three contrast-safe derived tokens exist for the cases the raw fill colors don't cover: `--app-accent-text`/`--app-highlight-text` are the accent/highlight colors nudged so they clear WCAG AA as *text on the page background* (reach for these on copy and icons, `--app-accent`/`--app-highlight` on solid fills); `--app-highlight-foreground` is a dedicated dark-ink color for text sitting *on top of a solid `--app-highlight` fill* (e.g. an avatar badge) — it can't reuse `--app-foreground` because that flips to light text in dark mode, which fails contrast against the mid-brightness highlight green in both themes.
- **App light/dark mode** — `src/lib/appTheme.ts` (zustand, initialized at module load) writes `data-theme="light"|"dark"` onto `document.documentElement`, persists the choice to `localStorage`, and defaults to `prefers-color-scheme` until the user picks a side explicitly. `[data-theme='dark']` in `index.css` overrides only the `app-*` values — `slide-*` deck themes are authored per deck and deliberately unaffected, so a light deck still previews light inside a dark editor. Tailwind's `dark:` variant is rebound to this attribute via `@custom-variant` at the top of `index.css`, so `dark:` utilities follow the in-app toggle rather than the OS setting. `components/ui/ThemeToggle.tsx` is the switch. Note: two surfaces are deliberately hardcoded always-dark and do **not** follow this toggle — the auth screens' `AuthVisualPanel` (the animated left panel on `/login`, which uses the *light* palette's own hex values directly in its styles) and the dashboard's `AppSidebar` rail (`components/home/AppSidebar.tsx`, white-alpha values over a fixed near-black). Both are fixed structural/brand statements: the dashboard layout is built around a dark rail against light content, and flipping the rail in light mode would collapse that contrast. Use `ThemeToggle`'s `onDark` prop for controls placed on either surface.
- **`slide-*`** (`--slide-background`, `--slide-accent`, `--font-slide-heading`, `--radius-slide`, `--shadow-slide`, …) — the *deck's* visual theme, applied only inside a scoped `ThemeProvider` wrapper (`components/theme/ThemeProvider.tsx`), never on `document.documentElement`. `ThemeProvider` renders a `display: contents` div and calls `applyTheme(theme, thatDivRef)` (`lib/theme-tokens.ts`), which sets the `--slide-*` custom properties (plus Tailwind's own global `--spacing` multiplier) as inline styles on that div. Because CSS custom properties cascade through `display: contents` elements, every `bg-slide-*`/`font-slide-*`/`rounded-slide-*` class *inside* that subtree picks up the scoped values, while everything outside it keeps the `:root` fallback. `layouts/*` components use `slide-*` classes exclusively; `components/ui/*` (shared chrome primitives) use `app-*` exclusively.
- Practical effect: switching a deck's theme (`ThemePanel`, now a **preset-only** picker — no manual color/font/radius/spacing controls) restyles only the cards wrapped in that `ThemeProvider` instance, never the surrounding editor UI. `ThemeProvider` is instantiated separately around `CardCanvas` and around the sidebar's card thumbnails (and again standalone in `PresentPage`), each reading the same `store.theme`.
- `lib/theme-tokens.ts` also exports `darken()` (hex→HSL→hex) used to derive `--slide-canvas-background` (and the app's own static `--app-canvas`) — the page background sits a few HSL-lightness points below the card background so cards read as floating panels with a shadow, in both light and dark presets.
- `BUILTIN_THEMES` (5 presets: Minimal, Editorial, Midnight, Bold, Sage) is the only source of themes — there's no user-created/custom-theme storage anymore.

### Dashboard layout (`pages/HomePage.tsx`)

A two-column app shell: an always-dark `AppSidebar` rail (logo, search, nav slot, account footer) beside a light main column. Below `lg` the rail becomes an off-canvas drawer driven by `open`/`onClose` from `HomePage` — there is deliberately no second, duplicated mobile header, so the markup has one source of truth.

- The rail's `<nav>` holds one **Workspace** section: `Overview` (routes to `/`) and `Drafts` (routes to `/drafts`, count badge from `useDrafts()` read inside `AppSidebar` itself rather than threaded through every page that renders the rail). `AppSidebar` exports `SidebarSection` and `SidebarLink`, already carrying the rail's styling (active pill, count badges), for further groups.
- Deck **search lives in the rail**, not in the panel toolbar, and binds ⌘F / Ctrl+F (the shortcut is advertised by a `<kbd>` chip in the field, so it has to actually work).
- The main column is a title/subtitle block above one bordered panel. The panel's toolbar strip holds a `ViewTabs` segmented switcher (`grid` | `list`) on the left and `FilterMenu` + the New-presentation CTA on the right.
- `components/home/deckFilters.ts` owns the view/sort/recency types and `selectDecks()`, which does search + filter + sort in a single pass so the grid and list views can't drift apart. Anything zero-result routes to `NoDeckMatches`, whose reset clears the search *and* the filters.
- Cards inside the panel use `border border-app-border` + `shadow-sm` rather than the full `shadow-app`; the deep shadow reads as card-in-card against the panel's own surface.

### Editor layout (`pages/EditorPage.tsx`)

Two independent slide-in/out side panels, not a shared mode switcher: a left outline panel (`CardOutlineSidebar.tsx`) and a right `Theme` panel, both animated via width transition (`w-0` ↔ fixed width, `overflow-hidden`) and able to be open simultaneously. The right panel is toggled from `TopBar`; the left panel floats (rounded corners, margin, shadow — not flush against the window edge) and is toggled by its own arrow button pinned to the vertical center of its right edge, not a `TopBar` button.

`CardOutlineSidebar`'s thumbnails are **not screenshots** — each is the real `LayoutRenderer` output rendered at a fixed offscreen size (800×450) and shrunk with `transform: scale()`, so they're always pixel-accurate to the live card and update instantly with theme/content changes.

### Persistence (Supabase)

`supabase/migrations/0001_init.sql` defines `presentations`, `cards`, and `themes` (the `themes` table is legacy/unused now that custom themes were removed — harmless to leave, not read from). `0002_add_visual_style.sql` adds `cards.visual_style` (`not null default 'structured'`) — run it against any project created before this field existed. RLS on every table is scoped to `owner_id = auth.uid()`, with `cards` checked via a join back to its parent `presentations` row. `store/presentationStore.ts` debounces text/theme field saves (`scheduleSave`, 500ms) but persists structural changes (card delete/reorder) immediately.

### Auth

`src/store/authStore.ts` is a zustand store, initialized once at module load (subscribing to `supabase.auth.onAuthStateChange`), exposing `user`/`status` plus `signUp`/`signIn`/`signOut`/`resetPasswordForEmail`/`updatePassword`. `resolveAuthState()` treats a session where `session.user.is_anonymous` is `true` the same as no session at all — this matters because browsers that used the app before this feature shipped may still be holding a leftover anonymous Supabase session in `localStorage`, and without this check that stale session would silently satisfy `RequireAuth` and skip the login screen entirely. `LoginPage.tsx` (route `/login`) handles login, signup, and forgot-password as one page via local mode state, rather than three separate routes. `ResetPasswordPage.tsx` (route `/reset-password`) is the landing page for the password-reset email link — Supabase's client auto-detects the recovery session from the URL. Decks created under the old anonymous-auth model (before this feature) are orphaned rows in Supabase, invisible to any real account under RLS — harmless to leave, or delete manually from the Supabase dashboard.

### Path alias

`@/*` → `src/*` (configured in both `tsconfig.app.json` and `vite.config.ts`).

### TypeScript strictness notes

`tsconfig.app.json` has `verbatimModuleSyntax: true` (type-only imports must use `import type`) and `erasableSyntaxOnly: true` (no TS constructor-parameter-property shorthand, e.g. `constructor(private x: string)` — assign fields in the constructor body instead).
